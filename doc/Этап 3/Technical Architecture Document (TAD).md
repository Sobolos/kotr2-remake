Technical Architecture Document (TAD)
Проект: Дальнобойщики 2 Remake (King of the Road Remake)
Версия: 1.0
Дата: 3 августа 2026
Статус: Черновик для обсуждения
1. Цели и принципы архитектуры
1.1. Основные цели
Разделить симуляцию (логика игры) и презентацию (графика, звук, физика UE5)
Обеспечить лёгкий перенос ядра игры из standalone-прототипа в Unreal Engine
Создать архитектуру, которая поддерживает моддинг
Обеспечить производительность при 51 водителе, 11 городах, сотнях грузов и активном рынке
Сделать систему тестируемой (unit-тесты для логики)
Позволить параллельную разработку (один делает экономику, другой — UI, третий — AI)
1.2. Ключевые принципы
Separation of Concerns (Разделение ответственности)
Каждый модуль отвечает только за свою область. Экономика не должна знать про графику, AI не должен знать про UI.
Platform Independence (Независимость от платформы)
Ядро игры (симуляция) не должно зависеть от Unreal Engine. Оно должно работать как standalone-библиотека, которую потом подключают к UE.
Data-Driven Design (Управление через данные)
Все параметры баланса, характеристики грузовиков, водителей, городов, грузов должны быть в данных (JSON/DataAsset), а не в коде.
Deterministic Simulation (Детерминированная симуляция)
При одинаковых входных данных и seed симуляция должна давать одинаковый результат. Это нужно для тестов, отладки и возможных сетевых фич.
Event-Driven Communication (Событийное взаимодействие)
Модули общаются через события, а не через прямые вызовы. Это снижает связанность.
Testability (Тестируемость)
Вся логика должна быть покрыта unit-тестами. Это критично для сложной симуляции с экономикой и рисками.
2. Слои архитектуры
Архитектура делится на три основных слоя:
┌─────────────────────────────────────────────────┐
│  Presentation Layer (UE5)                       │
│  - Actors, UI, Rendering, Physics, Audio        │
│  - Input handling                               │
│  - Camera systems                               │
│  - Weather visuals                              │
└─────────────────────────────────────────────────┘
                      ↕
┌─────────────────────────────────────────────────┐
│  Adapter Layer (Integration)                    │
│  - UE Subsystems wrapping Core                  │
│  - Event translators (Core events → UE events)  │
│  - Data loaders (JSON → UDataAsset)             │
└─────────────────────────────────────────────────┘
                      ↕
┌─────────────────────────────────────────────────┐
│  Core Layer (Simulation / Domain Logic)         │
│  - Pure C++ (no UE dependencies)                │
│  - Economy, Contracts, Drivers, Factions, Risk  │
│  - Time system, Save system                     │
│  - Event system, State management               │
└─────────────────────────────────────────────────┘
2.1. Core Layer (Ядро симуляции)
Это сердце игры. Здесь живёт вся логика:
Время и игровой цикл
Экономика городов
Генерация и управление контрактами
Управление водителями (51 именной + AI-конкуренты)
Фракции и репутация
Риск-директор (бандиты, милиция, события)
Рация (логика сообщений, выборов, последствий)
Рынок и контроль >51%
Сохранения
Требования:
Чистый C++ (стандарт C++20)
Никаких зависимостей от Unreal Engine
Только стандартная библиотека + лёгкие header-only библиотеки (nlohmann/json, spdlog)
Полное покрытие unit-тестами (doctest или Catch2)
2.2. Adapter Layer (Слой интеграции)
Это мост между Core и UE5:
UGameInstanceSubsystem обёртки вокруг Core-модулей
Конвертация событий Core в UE-события (деlegates)
Загрузка данных из JSON в UDataAsset / UDataTable
Синхронизация состояния (например, позиции грузовика из Core в Actor)
Требования:
Зависит и от Core, и от UE5
Минимальная логика — только интеграция
Чёткие границы: Adapter не должен принимать геймплейные решения
2.3. Presentation Layer (Слой презентации)
Это всё, что видит и слышит игрок:
Грузовики как физические объекты (Chaos Vehicle)
Прицепы и грузы
AI бандитов, милиции, трафика (Behavior Trees)
UI (UMG / CommonUI)
Звук (MetaSounds)
Погода и освещение
Камера и управление
Level Design (города, дороги, POI)
Требования:
Полностью зависит от UE5
Не содержит бизнес-логики
Реагирует на события из Core через Adapter
3. Модули Core Layer
3.1. TimeSystem (Система времени)
Ответственность:
Игровое время (минуты, часы, дни, недели)
Ускорение времени (1x, 2x, 4x, пауза)
События времени (новый час, новый день, конец недели)
Синхронизация с реальным временем (1 игровая минута = X реальных секунд)
Взаимодействие:
Публикует события: OnGameHour, OnGameDay, OnGameWeek
Другие модули подписываются на эти события
Примеры использования:
Экономика обновляет цены каждый игровой час
Водители устают каждую минуту
Бандиты чаще появляются ночью
3.2. EconomySystem (Экономическая система)
Ответственность:
Состояние городов (производство, потребление, запасы)
Динамика цен (спрос/предложение)
Топливные кризисы (АЗС без топлива)
Доступность запчастей (СТО)
Генерация заказов на основе экономики
Взаимодействие:
Подписывается на OnGameHour для симуляции
Публикует события: OnPriceChanged, OnStockout, OnContractGenerated
Запрашивает данные у ContractSystem для создания заказов
Режимы работы:
Living Economy (Живая экономика): Полная симуляция, цены меняются динамически
Classic Economy (Классическая экономика): Упрощённая, топливо и запчасти всегда доступны
3.3. ContractSystem (Система контрактов)
Ответственность:
Генерация заказов (обычные, срочные, опасные, нелегальные)
Управление активными контрактами
Расчёт оплаты (расстояние, масса, риск, срочность)
Отслеживание дедлайнов
Штрафы за провал
Конкуренция с AI-водителями
Взаимодействие:
Запрашивает данные у EconomySystem (цены, спрос)
Запрашивает данные у RiskSystem (оценка риска маршрута)
Публикует события: OnContractGenerated, OnContractCompleted, OnContractFailed
3.4. DriverSystem (Система водителей)
Ответственность:
Управление 51 именным водителем
Найм и увольнение
Назначение на грузовики и рейсы
Лояльность, мораль, усталость
Скрытые черты (вор, предатель, профессионал)
Конфликты между водителями
AI-поведение нанятых водителей (когда они не рядом с игроком)
Взаимодействие:
Подписывается на OnGameHour для обновления состояния
Публикует события: OnDriverHired, OnDriverFired, OnDriverBetrayed, OnDriverDeliveredCargo
Запрашивает данные у ContractSystem для назначения рейсов
3.5. FactionSystem (Система фракций)
Ответственность:
Репутация игрока с фракциями (Кайманы, Братва Приозёрская, Горные, Милиция)
Зоны влияния фракций
Услуги фракций (крыша, атака конкурента, взятки)
Динамика отношений (вражда, нейтралитет, партнёрство)
Взаимодействие:
Подписывается на события игрока (доставка нелегального груза, оплата взятки)
Публикует события: OnReputationChanged, OnFactionWarStarted
Предоставляет данные RiskSystem для оценки опасности маршрута
3.6. RiskSystem (Риск-директор)
Ответственность:
Оценка риска маршрута (бандиты, милиция, погода, дорога)
Генерация событий (засады, остановки, поломки)
Балансировка риска и награды
Кулдауны событий (не слишком часто)
Режиссёрская логика (напряжение нарастает, кульминация, разрядка)
Взаимодействие:
Запрашивает данные у FactionSystem (зоны влияния, репутация)
Запрашивает данные у TimeSystem (ночь/день, погода)
Запрашивает данные у ContractSystem (ценность груза, нелегальность)
Публикует события: OnRiskEventTriggered (засада, остановка, поломка)
3.7. RadioSystem (Система рации)
Ответственность:
Логика сообщений (бандиты, милиция, водители, конкуренты)
Контекстные сообщения (зависят от ситуации)
Варианты ответа (заплатить, договориться, пригрозить)
Последствия выбора (репутация, деньги, события)
Кулдауны и частота сообщений
Взаимодействие:
Подписывается на события из всех систем (засада, остановка, доставка)
Публикует события: OnRadioMessageSent, OnRadioChoiceMade
Запрашивает данные у FactionSystem, RiskSystem, DriverSystem
3.8. MarketSystem (Система рынка)
Ответственность:
Отслеживание доли рынка игрока (грузоподъёмность автопарка)
Доли конкурентов
Динамика контроля рынка
Условие победы (>51% рынка)
Статистика (тонно-километры, доходы, расходы)
Взаимодействие:
Подписывается на OnContractCompleted для обновления статистики
Публикует события: OnMarketShareChanged, OnVictoryConditionReached
3.9. SaveSystem (Система сохранений)
Ответственность:
Сериализация состояния всех модулей
Версионирование сохранений
Автосейвы (конец дня, важные события)
Ручные сейвы
Миграция старых версий
Взаимодействие:
Запрашивает состояние у всех модулей
Восстанавливает состояние при загрузке
4. Форматы данных (высокоуровнево)
4.1. Принципы
Все данные в JSON (для моддинга и прототипирования) или UDataAsset (для UE)
Стабильные ID (snake_case, без пробелов, без русских букв)
Все тексты вынесены в локализацию (ключи loc_city_yuzhny_name)
Числовые параметры баланса — в данных, не в коде
Валидация данных при загрузке
4.2. Основные типы данных
Города (CityData):
ID, название, описание
Специализация (производит/потребляет)
Уровень опасности
Зоны влияния фракций
Доступные услуги (АЗС, СТО, мотель, чёрный рынок)

Грузы (CargoData):
ID, название, категория
Масса, объём
Базовая ставка за тонно-километр
Уровень опасности
Легальность

Водители (DriverData):
ID, имя, портрет, озвучка
Характер (теги: calm, aggressive, professional, psycho)
Скрытые черты (теги: thief, traitor, loyal)
Базовые навыки (вождение, ремонт, переговоры)
Предпочтения по грузам

Грузовики (TruckData):
ID, название, класс
Максимальная скорость, мощность двигателя
Расход топлива, объём бака
Максимальная грузоподъёмность
Надёжность
Стоимость ремонта

Маршруты (RouteData):
ID, от/до
Расстояние, тип покрытия
Базовая скорость
Уровень опасности
Зоны влияния фракций
POI на маршруте

События (EventData):
ID, название, тип
Условия срабатывания
Варианты выбора
Последствия
Кулдаун

5. Взаимодействие модулей (примеры потоков)
5.1. Поток "Игрок принимает контракт"
1. PlayerUI → ContractSystem.AcceptContract(contractId)
2. ContractSystem → RiskSystem.EvaluateRouteRisk(route)
3. RiskSystem → FactionSystem.GetFactionInfluence(route)
4. RiskSystem → TimeSystem.GetTimeOfDay()
5. RiskSystem возвращает оценку риска
6. ContractSystem публикует событие OnContractAccepted
7. DriverSystem (если назначен водитель) → DriverState.InTransit
8. RiskSystem подписывается на события маршрута
9. TimeSystem запускает таймер рейса

5.2. Поток "Бандитская засада"
1. RiskSystem.DetectThreat(route, cargo, reputation)
2. RiskSystem → FactionSystem.GetFactionAggression("kaimany")
3. RiskSystem решает сгенерировать событие
4. RiskSystem публикует событие OnRiskEventTriggered(BanditAmbush)
5. RadioSystem подписывается → создаёт сообщение
6. RadioSystem → PlayerUI.ShowRadioMessage(choices)
7. Player делает выбор (заплатить/игнорировать)
8. RadioSystem публикует событие OnRadioChoiceMade
9. FactionSystem обновляет репутацию
10. EconomySystem (если груз потерян) → ContractSystem.FailContract

6. Требования к производительности
6.1. Core Layer
Симуляция одного игрового часа (все города, водители, контракты) — не более 16 мс (60 FPS)
Генерация контрактов для одного города — не более 1 мс
Оценка риска маршрута — не более 0.5 мс
Сохранение игры — не более 100 мс
6.2. Adapter Layer
Синхронизация состояния (Core → UE) — не чаще 10 раз в секунду для неактивных объектов
Для активных объектов (грузовик игрока) — каждый кадр
6.3. Presentation Layer
60+ FPS на целевом железе (Ryzen 5700X + RTX 4070 Ti)
Стриминг мира (World Partition) для 11 городов
Оптимизация AI (не все водители симулируются полностью)

  8. Версионирование и миграция
8.1. Версии данных
Каждый тип данных имеет версию:

{
  "version": "1.2",
  "type": "CityData",
  "id": "yuzhny",
  ...
}

8.2. Версии сохранений
{
  "save_version": 3,
  "game_time": {...},
  "cities": [...],
  ...
}

8.3. Миграция
При загрузке старых данных/сохранений запускаются миграционные функции:
SaveVersion1 → SaveVersion2 (добавлены водители)
SaveVersion2 → SaveVersion3 (изменена формула рынка)

9. Требования к моддингу
9.1. Что можно моддить
Города (добавлять новые)
Грузы (новые типы)
Водители (новые персонажи)
Грузовики и прицепы
События и рация
Баланс (цены, риски, зарплаты)
Карты (новые регионы)
9.2. Формат модов
Папка Mods/MyMod/
Файл mod.json с метаданными
Переопределение или добавление данных
Приоритет загрузки (базовая игра → моды)
9.3. Ограничения
Нельзя менять Core-логику (только данные)
Нельзя добавлять новые механики без модификации кода
Совместимость модов проверяется при загрузке
